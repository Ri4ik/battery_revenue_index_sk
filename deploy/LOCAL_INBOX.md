# SEPS Excel → папка incoming → Docker worker → dashboard

## Что реализовано

Используются те же три сервиса: PostgreSQL, worker и dashboard. Worker может принимать SEPS XLSX из папки сервера вместо OneDrive. Источники OKTE/ENTSO-E по API остаются доступны. Дополнительная таблица интервалов и другие изменения схемы БД не требуются.

```text
incoming/ (SEPS: объёмы Up/Down)
   → worker → ENTSO-E A84 (цены активации Up/Down за даты файла)
            → ENTSO-E A15 (недостающие цены/объёмы резервирования)
            → объединение по UTC-интервалам → PostgreSQL
            → расчёт → проверка публикации → dashboard
            → reports/local_inbox/ (JSON + TXT)
```

В Windows рабочая папка текущего развёртывания:

```powershell
cd C:\Users\lopat\Desktop\battery_revenue_index_sk_unified
```

Все команды ниже используют существующий Compose project `bri-db-pipeline`, чтобы подключиться к тем же томам и данным.

## Поддерживаемый Excel

Отчёт SEPS/Damas «Regulačná elektrina (denná)», лист `aFRR`. Поддерживаются два формата.

**Новый, пять колонок:** дата, час, четверть часа, объём Up, объём Down. Цены вручную добавлять не нужно: worker загружает их из ENTSO-E (`documentType=A84`, `processType=A16`, `businessType=A96`, SEPS area). Даты берутся из фактических строк файла, включая первый день. Для запроса нужен действующий `ENTSOE_API_KEY` в приватном `.env`. Ключ не записывается в отчёты.

**Архивные файлы в `marketdata/SepsDamasEnergy/raw` содержат цены.** Это проверено на восьми XLSX в текущем проекте и в `PROJ_2_AL_DB`. В семиколоночном варианте порядок такой:

1. Дата.
2. Час.
3. Четверть часа.
4. Объём Up, MWh.
5. Цена Up, EUR/MWh.
6. Объём Down, MWh.
7. Цена Down, EUR/MWh.

Например, `08_seps_damas_regulacna_elektrina_2026_3_4_5.xlsx`, лист aFRR, первая строка за 02.03.2026: объём Up 1.931, цена Up 103.3305, объём Down 0.004, цена Down 8.9. Заголовки цен в оригинале — `Cena [€]`. Файл `06_...2025_11_12.xlsx` имеет девять колонок: для каждого направления отдельные колонки особой и стандартной цены. Парсер определяет объёмы и цены по заголовкам; разные одновременно заполненные цены без разбивки объёма по продуктам отклоняются.

**Как работала прежняя версия:** `tools/importaFRR.py` получал ENTSO-E capacity; `tools/import_seps_damas_energy.py` читал из архивного SEPS Excel объёмы и цены энергии и создавал дневной CSV; `markets/aFRR_market.py` использовал этот CSV и отдельные данные capacity для расчёта aFRR. В инструменте ENTSO-E также был запрос A84 и сохранён успешный ответ, но прежний SEPS-расчёт не подставлял его цены в Excel автоматически. Новый пятиколоночный файл обрабатывает добавленная ветка worker с автоматическим A84.

Сверка сохранённого A84 за 23.05.2026 с SEPS CSV дала 176 совпадений из 176 сопоставимых цен Up/Down. Сопоставление выполнено по UTC-моментам: архивный API-ответ покрывает UTC-сутки, CSV — словацкие локальные сутки. Это подтверждает совместимость источников на проверенном участке, но не доступность июньского API.

Парсер определяет начало данных по строкам, а не по фиксированному числу строк заголовка. Числа проверяются; при ненулевом объёме отсутствующая цена отклоняется. Пустой объём считается отсутствием активации; пустая цена допустима только при нулевом соответствующем объёме. Нативные сутки проверяются на полное число 15-минутных интервалов (включая DST).

Нельзя использовать объём Down как цену Up или подставлять нулевые отсутствующие цены при ненулевой активации. Отчёт «Kontrakty PpS – denné» с мощностями резервирования не является входом этого импортёра.

**Единицы нового экспорта:** worker читает заголовки MW/MWh. В проверенном июньском файле лист aFRR подписан MWh, но его значения вместе с mFRR на всех 2880 интервалах точно совпадают с разделом `Spolu / 12.3.E [MW]`. Только при полном совпадении этих листов worker трактует исходные значения как MW и явно переводит в MWh (`MW × 0.25 часа`). Обе единицы и основание преобразования записываются в JSON/TXT. Несовпадающий контроль отклоняется. Исходный Excel не исправляется.

**Выбор цен:** не смешиваются разные процессы, продукты, категории и типы ресурсов. A67/A68 и CBMP A08 не подставляются вместо профиля A16. Нужны EUR/MWh и полное покрытие интервалов с активацией. Несколько различающихся полных профилей означают ожидание уточнения. Изменяющиеся минутные цены нельзя точно соединить с одним суммарным 15-минутным объёмом без минутных объёмов: такой случай тоже остаётся в ожидании.

Если API недоступен, цен нет или профиль неоднозначен, файл получает `waiting_api` и остаётся в `incoming/.processing/`. Повтор той же команды продолжает обработку, заново копировать файл не нужно. Уже скачанные пригодные XML/ZIP используются из raw-архива по датам и версии политики выбора. Автоматическая повторная проверка поздних исправлений уже закешированных цен в этот релиз не входит.

Парсеры: `seps-damas-xlsx-v3` для архивного файла с ценами; `seps-volumes-entsoe-a84-v1` для объединённых данных. Политика A84 v2 учитывает категорию цены внутри Point реального XML. В метаданных сохраняются ссылки и SHA-256 исходного Excel и каждого документа ENTSO-E. Схема БД не меняется; исторические записи автоматически не перезагружаются.

## Настройка каталогов

### Где находится worker

Worker — сервис `worker` в `docker-compose.yml`, а не отдельный файл `worker.py`. Его постоянно работающий процесс — Supercronic. По расписанию или по Docker-команде он запускает `python -m bri.pipeline`.

| Код | Что делает |
|---|---|
| `bri/pipeline.py`, `main()` | Координирует импорт, API, расчёт и публикацию. |
| `bri/local_inbox.py`, `LocalInboxRun.intake()` / `finish()` | Забирает Excel, сохраняет журнал, отчёт и состояние очистки. |
| `bri/importers/seps.py`, `inspect_local_xlsx()` / `import_local_xlsx()` | Читает формат SEPS и соединяет объёмы с ценами. |
| `bri/importers/entsoe_energy.py`, `load_for_volumes()` | Получает/кеширует A84 и сопоставляет цены по UTC-интервалу и направлению. |
| `bri/importers/entsoe.py`, `import_range()` | Получает A15 capacity. |
| `bri/readiness.py` / `bri/calc.py` | Проверяет готовность дней, считает и публикует результаты. |
| `tools/results_db.py`, `load_published()` | Читает `bri.published_daily_total` для дашборда. |

Совпадения только календарной даты недостаточно: важны интервал, Up/Down, продукт и часовой пояс. Не переносятся цены одного дня в другой и не подставляются цены capacity вместо energy.

Параметры `.env` (без паролей в этом примере):

```dotenv
BRI_FILE_SOURCE=local
BRI_INBOX_HOST=./incoming
BRI_REPORTS_HOST=./reports/local_inbox
BRI_LOCAL_MIN_AGE_SECONDS=10
BRI_DELETE_AFTER_SUCCESS=0
```

Монтирование worker:

| На сервере/компьютере | Внутри worker |
|---|---|
| `incoming/` | `/data/inbox` |
| `reports/local_inbox/` | `/data/reports` |

Пути хоста можно задать абсолютными. Папки входящих данных и отчётов должны быть разными. На Linux appuser контейнера (UID 1000) нужны права чтения/записи. Каталоги исключены из Git и Docker build context. Токен OneDrive локальному режиму не нужен.

`BRI_FILE_SOURCE=local` выбирает локальный источник также для ежедневного cron. Для ручного запуска можно независимо передать `--source local`, `--source onedrive` или `--source none`. `none` отключает только файловый источник; API отдельно отключаются флагом `--skip-api`.

## Загрузка файла в Windows

Из папки проекта:

```powershell
.\tools\upload_local_input.ps1 -Path "C:\Users\lopat\Downloads\my_seps_export.xlsx"
```

Если локальная политика PowerShell блокирует скрипт, его можно выполнить отдельным процессом:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\upload_local_input.ps1 -Path "C:\Users\lopat\Downloads\my_seps_export.xlsx"
```

Скрипт копирует файл в `.part`, сверяет SHA-256 и атомарно переименовывает в `.xlsx`. Оригинал в Downloads сохраняется. При совпадении имени уже загруженного файла скрипт выдаёт ошибку вместо перезаписи. Можно явно задать `-Inbox`.

После завершения копирования подожди 10 секунд: worker пропускает слишком свежие файлы. Временные `.part` и Excel lock-файлы `~$...` не обрабатываются. Загружать можно и вручную, но сначала нужно закончить копирование и только потом запускать обработку.

## Запуск и отчёт

Обычный запуск со скачиванием необходимых API-данных:

```powershell
docker compose -p bri-db-pipeline exec worker python -m bri.pipeline --source local
```

При обычном ручном запуске без `--from/--to` обрабатываются даты загруженных/ожидающих файлов; cron продолжает обновлять также недавние дни других рынков через OKTE. Если все необходимые API-данные уже есть в БД/raw-кеше, можно отключить сеть. Например, для июня 2026:

```powershell
docker compose -p bri-db-pipeline exec worker python -m bri.pipeline --source local --skip-api --from 2026-06-01 --to 2026-06-30
```

Для удаления после полной успешной обработки:

```powershell
docker compose -p bri-db-pipeline exec worker python -m bri.pipeline --source local --delete-after-success
```

`--keep-files` принудительно сохраняет входные файлы, даже если удаление включено в окружении. Переопределить пути внутри контейнера можно через `--inbox` и `--report-dir`.

Логи печатают пути отчётов, например:

```text
/data/reports/local_12_20261104_120000.json
/data/reports/local_12_20261104_120000.txt
```

На хосте это файлы в `reports/local_inbox`. Каждый запуск получает свой номер pipeline и пару отчётов. Журнал `.state/` позволяет продолжить обработку после перезапуска: не удаляй его, пока есть незавершённые файлы. Отчёты сами по себе не являются резервной копией БД.

JSON/TXT содержат имя, хеш, реальные даты файла, исходное число строк, количество новых строк, artifact_id/batch_id, единицы объёмов, документы и профили цен ENTSO-E, число опубликованных результатов, причины ожидания, ошибки и состояние удаления. Для local-режима exit code 0 означает полный успех либо отсутствие новых задач, 1 — ошибку/ожидание/частичный результат, 2 — уже работающий pipeline.

## Что происходит с файлами

```text
incoming/
├── my_seps_export.xlsx          # ещё не захвачен worker
├── .processing/<id>.xlsx        # импортирован или ожидает расчёта/очистки
└── errors/<id>_<original>.xlsx  # неверный формат, сохранён для исправления
```

Worker сначала фиксирует намерение в журнале, затем атомарно перемещает файл в `.processing`. Новый файл, загруженный позже под тем же именем, не перезаписывается и не удаляется вместо старого. Символьные ссылки не импортируются.

При обычном успешном запуске без удаления файл возвращается в incoming; повторный запуск узнает содержимое по хешу и не создаёт дубли исходных значений. Если данные уже импортированы, но не хватает capacity либо расчёт не удался, файл остаётся в `.processing`. После появления необходимых входов нужно запустить команду повторно: импорт не повторяется без необходимости, расчёт продолжается.

При `--delete-after-success` проверяется, что для всех фактических дат файла и всех конфигураций батареи опубликованы aFRR total текущей версии модели, соответствующие актуальным хешам energy/capacity. Просто `import_batch=success` или успешного общего calc_run недостаточно.

До удаления сохраняется отчёт и состояние `cleanup_pending`. Затем удаляется raw-копия, созданная этим локальным режимом, и именно захваченный входной файл. Метаданные source_artifact сохраняют исторический путь и `raw_state=purged`, время очистки и хеш. Чтение заведомо удалённого оригинала выдаёт явное сообщение. Исходные нормализованные значения, результаты и журналы PostgreSQL сохраняются.

Если такой артефакт уже был получен через OneDrive/старую миграцию, его существующий архив не удаляется (`retained_existing`). Общая raw-копия другого артефакта также сохраняется (`retained_shared`). Очистка не распространяется автоматически на старые API-ответы и чужие архивы. Повторно загруженный локальный оригинал может быть обработан вновь новой версией парсера.

Сбой удаления оставляет `cleanup_pending`; повторный запуск завершает недостающие операции. Ошибка записи отчёта перед очисткой предотвращает удаление. Плохие XLSX помещаются в errors и не удаляются автоматически.

## Проверка в DBeaver и на сайте

Для нового пятиколоночного файла при удалении очищаются локальные raw-копии Excel и объединённого JSON; ссылки, хеши и нормализованные данные остаются в PostgreSQL. Исходные XML/ZIP ENTSO-E сохраняются как кеш и доказательство использованных цен. Они не удаляются общей очисткой локального Excel.

```sql
SELECT delivery_day, config_code, market, revenue_eur, run_id
FROM bri.published_daily_total
WHERE market = 'AFRR'
  AND delivery_day BETWEEN DATE '2026-06-01' AND DATE '2026-06-30'
ORDER BY delivery_day, config_code;

SELECT pipeline_run_id, started_at, finished_at, status, messages
FROM bri.pipeline_run
ORDER BY pipeline_run_id DESC
LIMIT 10;
```

Для полного месяца и четырёх конфигураций ожидается 120 опубликованных дневных результатов, если доступны все входы и расчёт завершён. На сайте обнови страницу и выбери июнь 2026. Не делай вывод об успехе только по наличию Excel в папке или факту запуска контейнера.

## Перенос на Linux-сервер

1. Подготовить каталоги `/srv/battery-index/incoming` и `/srv/battery-index/reports`, доступные UID 1000.
2. Задать абсолютные `BRI_INBOX_HOST` и `BRI_REPORTS_HOST` в `.env` сервера.
3. Запустить PostgreSQL, worker и dashboard с постоянными томами и настроенной БД.
4. Передать Excel с ноутбука по SFTP/SCP сначала как `name.xlsx.part`, затем переименовать в `name.xlsx` в той же серверной папке.
5. По SSH выполнить Docker-команду либо дождаться 16:00 Europe/Bratislava.
6. Получить TXT/JSON из reports и проверить публикацию.

Локальная папка ноутбука сама по себе не видна Docker на удалённом сервере: файл нужно сначала передать. Отдельный S3-сервис для этого режима не используется.

## Тестирование разработчиком

На 04.11.2026 образ `battery-revenue-index-sk:local-entsoe-rawfix-20261104` прошёл 70 тестов. Реальный июньский Excel успешно обработан pipeline 7: 30 документов A84, 2880 входных интервалов, 120 опубликованных дневных aFRR результатов. Входная загруженная копия и локальные raw-копии очищены после публикации; исходник Downloads и API-кеш сохранены. Подробная проверка: `reports/local_inbox/RAW_FLOW_REVIEW_20261104.md`. Отдельно обнаруженные ошибки исторических данных не переимпортировались автоматически.

`tests/test_local_inbox.py` проверяет новые и повторные файлы, исправления, ожидание capacity, отчёт до удаления, ошибки очистки, защиту от ссылок и параллельных запусков, прежние архивы, восстановление захвата, старые дни вне API-окна, новую выгрузку только с объёмами и заголовок переменной длины.

Тестовая `TEST_DATABASE_URL` должна указывать только на отдельную одноразовую БД: фикстуры удаляют её схему bri. Рабочую battery_revenue_index для pytest не использовать.
